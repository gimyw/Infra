## 2. 온프레미스 성능 한계 분석

### 2.1 컴퓨팅 한계

| 항목 | 현행 | 한계 |
| --- | --- | --- |
| App 서버 | 2vCPU / 2GB 단일 VM | JVM + MinIO 동시 구동 시 메모리 부족. 동시 요청 50건 이상에서 GC 압박 |
| Web 서버 | 2vCPU / 2GB 단일 VM | dev 서버(Vite) 구동으로 프로덕션 서빙 불가 |
| DB 서버 | 2vCPU / 2GB 단일 VM | 커넥션 증가 시 메모리 부족. shared_buffers 512MB 이하 제한 |

### 2.2 성능 예측 (온프레미스 최대 처리량)

#### 일반 API 요청

| 지표 | 예상치 |
| --- | --- |
| 최대 처리량 | ~30~60 req/s (단일 Task, JVM 힙 제한) |
| 동시 접속자 | ~100~200명 |
| DAU 환산 | ~500~1,500명 |

#### Bedrock 이미지 생성 (외부 API 호출)

| 지표 | 예상치 |
| --- | --- |
| 동시 처리 | ~5~10건 (Tomcat 스레드 점유 + 메모리 부족) |
| 분당 처리량 | ~30~60건/분 |

#### 한계 도달 시 증상

- JVM OutOfMemoryError (이미지 Base64 응답 + 힙 부족)
- DB 커넥션 풀 고갈 (HikariCP timeout)
- 전체 서비스 응답 지연 → 타임아웃

### 2.3 인프라 한계

| 항목 | 한계 | 영향 |
| --- | --- | --- |
| 단일 호스트 SPOF | PC 1대 장애 = 전체 서비스 중단 | 가용성 0% (이중화 없음) |
| 수평 확장 불가 | VM 추가해도 로드밸런싱 없음 | 트래픽 증가 대응 불가 |
| CentOS 7 EOL | 보안 패치 종료 (2024.06) | 보안 취약점 노출 |
| 백업 없음 | 스냅샷/백업 정책 미수립 | 데이터 유실 위험 |
| TLS 미적용 | HTTP 평문 통신 | 전송 구간 보안 없음 |
| firewalld OFF | 계층 격리 미성립 | DB 외부 노출 |

## 3. 마이그레이션 필요성 (Why ECS?)

### 3.1 비즈니스 관점

| 문제 | ECS 전환 시 해결 |
| --- | --- |
| 서비스 중단 위험 (SPOF) | Multi-AZ + 다중 Task로 고가용성 확보 |
| 사용자 증가 대응 불가 | Auto Scaling으로 트래픽에 따라 자동 확장/축소 |
| 보안 미비 (HTTP, 방화벽 OFF) | ALB HTTPS + Security Group으로 계층 격리 |
| 수동 배포 (jar 직접 실행) | CI/CD 자동 배포 (GitHub Actions → ECR → ECS) |
| 데이터 유실 위험 | RDS 자동 백업 + S3 내구성 99.999999999% |

### 3.2 기술 관점

| 항목 | 온프레미스 | ECS Fargate |
| --- | --- | --- |
| 확장성 | 수직 확장만 가능 (VM 스펙 UP) | 수평 확장 (Task 추가, Auto Scaling) |
| 가용성 | 단일 장애점 | Multi-AZ, 자동 복구 |
| 운영 부담 | OS 패치, JVM 관리, 디스크 관리 | 서버리스 (인프라 관리 불필요) |
| 배포 속도 | 수동 (10~30분) | 자동 (2~5분, 무중단) |
| 모니터링 | 없음 | CloudWatch 메트릭/로그/알람 |
| 보안 | 수동 설정 (firewalld) | 관리형 (SG, ACM, IAM) |
| 비용 모델 | 고정 (PC 상시 가동) | 종량제 (사용한 만큼) |

### 3.3 Bedrock AI 서비스 관점

| 항목 | 온프레미스 | ECS on AWS |
| --- | --- | --- |
| Bedrock 접근 | NAT 경유 (불안정, 지연) | 같은 AWS 네트워크 (저지연) |
| IAM 권한 | 불가 (Access Key 필요) | Task Role로 안전한 권한 부여 |
| 이미지 저장 | MinIO (단일 디스크) | S3 (내구성, CDN 연동) |

## 4. ECS 마이그레이션 스펙 정의

### 4.1 ECS Task 스펙

| 환경 | vCPU | Memory | Task 수 | Auto Scaling |
| --- | --- | --- | --- | --- |
| Dev | 0.5 | 1GB | 1개 (고정) | 없음 |
| Prod (초기) | 1 | 2GB | 2개 (min) | min 2 / max 6, CPU 70% 기준 |

#### 스펙 선정 근거

| 항목 | 근거 |
| --- | --- |
| vCPU 1 (Prod) | Bedrock 호출은 I/O 대기 위주. CPU 연산 적음. 0.5로는 GC + 동시 요청 시 부족 |
| Memory 2GB (Prod) | JVM 힙 1.4GB + Metaspace 128MB + OS 400MB. 이미지 Base64 응답 버퍼 여유 확보 |
| Task 2개 (min) | AZ별 1개 배치로 고가용성 최소 보장. 1개면 배포 시 서비스 중단 |
| Task 6개 (max) | Bedrock 동시 호출 한도 감안 시 6개 이상은 과잉 |

#### JVM 설정 (환경변수로 주입)

```
JAVA_OPTS=-Xms512m -Xmx1408m -XX:+UseG1GC -XX:MaxMetaspaceSize=128m
```

### 4.2 RDS 스펙

| 환경 | 인스턴스 | 스토리지 | Multi-AZ | 엔진 |
| --- | --- | --- | --- | --- |
| Dev | db.t3.micro | 20GB gp3 | 아니오 | PostgreSQL 16.4 |
| Prod | db.t3.small | 50GB gp3 | 예 | PostgreSQL 16.4 |

#### 스펙 선정 근거

| 항목 | 근거 |
| --- | --- |
| db.t3.small (Prod) | 온프레미스 2GB에서 정상 운영. t3.small(2GB)로 동일 수준 유지 |
| 50GB gp3 | 이미지 메타데이터 + 사용자 데이터. 초기 여유분 확보 |
| Multi-AZ | SPOF 해소. 자동 페일오버 |

### 4.3 ElastiCache 스펙

| 환경 | 노드 타입 | 노드 수 | Auto Failover |
| --- | --- | --- | --- |
| Dev | cache.t3.micro | 1 | 아니오 |
| Prod | cache.t3.small | 2 (Primary + Replica) | 예 |

#### 스펙 선정 근거

| 항목 | 근거 |
| --- | --- |
| cache.t3.small (Prod) | 세션/캐시 용도. 메모리 1.5GB면 초기 충분 |
| 2노드 | 고가용성. Primary 장애 시 Replica 승격 |

### 4.4 ALB 스펙

| 항목 | 설정값 | 근거 |
| --- | --- | --- |
| Idle Timeout | 120초 | Bedrock 이미지 생성 응답 15초+. 여유 확보 |
| Health Check Path | /api/v1/health | Spring Boot Actuator |
| Health Check Interval | 30초 | - |
| Deregistration Delay | 30초 | 배포 시 기존 요청 완료 대기 |
| HTTPS | ACM 인증서 (발급 후 활성화) | TLS 1.3 |

| 항목 | 설정값 |

| Target | 70% |
| Scale Out 쿨다운 | 60초 |

| 지표 | 온프레미스 | ECS |

### 7.4 스타트업 관점 핵심 차이

| 온프레미스 | 클라우드 (AWS) |
| --- | --- |
| 초기 수백만원 투자 필요 (자금 부담) | 초기 비용 $0, 매월 사용량만 과금 |
| 서버 장애 시 직접 대응 (새벽 콜 가능) | 자동 복구, Multi-AZ |
| 트래픽 급증 → 서버 추가 구매 대기 | Auto Scaling → 수 분 내 대응 |
| 개발자가 서버 관리에 시간 소모 | 개발에만 집중 가능 (생산성 ↑) |
| 피크 기준 장비 구매 → 평상시 유휴 낭비 | 사용한 만큼만 과금 |

| 스케일업만 가능 (서버 스펙 업) | 스케일아웃 가능 (Task 추가) |

### 7.5 1년 TCO (Total Cost of Ownership) 비교

```
온프레미스: 초기 $5,500 + 월 $1,060 × 12 = ~$18,220/년
AWS ECS:   초기 $0    + 월 $295  × 12 = ~$3,540/년

절감: ~$14,680/년 (약 80% 절감)
```

### 7.6 클라우드 전환으로 얻는 가치

| 얻는 것 | 스타트업 관점 가치 |
| --- | --- |
| 99.9%+ 가용성 | 서비스 신뢰도 → 사용자 이탈 방지 |
| 자동 확장 | 바이럴 시 서버 증설 걱정 없음 |
| 개발자 시간 확보 | 인프라 대신 제품 개발에 집중 → 출시 속도 ↑ |
| 보안 (HTTPS, IAM, SG) | 개인정보 보호, 투자 유치 시 기술 신뢰도 |
| 자동 백업/복구 | 데이터 유실 = 스타트업 사망. 자동 보호 |
| CI/CD 자동 배포 | 하루 여러 번 배포 가능, 빠른 피드백 루프 |
| 글로벌 확장 용이 | 해외 진출 시 리전 추가만으로 가능 |
